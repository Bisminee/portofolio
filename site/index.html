Case 01 Team project 2026

POS Tahu Morojoyo

A multi-branch point-of-sale and attendance system for a family food business

A Laravel 12 point-of-sale system with a Filament admin panel, cashier shifts, face-based attendance, multi-branch stock, and a Google Sheets export path.

  • Laravel 12
  • PHP 8.2
  • Filament 4
  • Livewire
  • Blade
  • MySQL
  • Google Sheets API
Source for POS Tahu Morojoyo (opens in a new tab)
Read the full case file

The problem

A tofu food business needs more than a cash register. Sales, shift attendance, branch stock, and owner reporting have to agree with each other — and a cashier should not be able to open the till before checking in.

The solution

A Laravel application that separates the public storefront from the operational back office. Cashiers authenticate, clock in with a face capture, and only then reach the POS. Owners manage branches, employees, menus, prices, and stock through Filament resources, while attendance is enforced in the route layer.

What is in the repository

  • Laravel 12 application with PHP 8.2, Livewire, and a Filament 4 administration panel.
  • Route middleware gates the POS behind a completed attendance check-in; the cashier route group also handles checkout and Google Sheets synchronisation.
  • Eloquent models and migrations cover branches, employees, tofu stock, menus, prices, menu composition, stock mutations, transactions, transaction items, shifts, and attendance.
  • Owner-facing screens enrol employee face data and export attendance recaps as CSV.
  • A public-facing section presents the home page, menu, about page, and contact page separately from the admin panel.

Technical decisions

  • Used Filament resources for back-office CRUD instead of hand-building every admin screen — domain work stays in models, operations stay auditable.
  • Put the attendance requirement in route middleware so the business rule cannot be bypassed by navigating directly to the cashier URL.
  • Modelled stock as both per-piece records and mutation history, leaving an audit trail rather than a single mutable counter.

Challenges

  • The schema evolved through many additive migrations (roles, branch ownership, soft-active flags, shift foreign keys, face photos) — the migration history documents that iteration.

Verifiable results

  • The repository contains the full application, migration set, and Filament resource layer. No production metrics are published, so none are claimed here.
Evidence note

Team repository. Commits and merges appear under the Bisminee account alongside other contributors; per-feature authorship is not documented, so this case file describes the system rather than claiming sole authorship.

Case 02 Team project 2026

Sera-Z

A Flutter wardrobe assistant that reads clothing from a photograph

A two-person Flutter project: photograph a garment, identify its type and colour, then receive outfit suggestions. A v1.0.0 Android build is published.

  • Flutter
  • Dart
  • Riverpod
  • go_router
  • camera
  • Material 3
  • Android
Source for Sera-Z (opens in a new tab) Download v1.0.0 APK (opens in a new tab) Android 7.0+; sideloading required.
Read the full case file

The problem

Choosing an outfit is a small decision with a lot of hidden context: what is clean, what matches, and what the item actually is. The team set out to turn a single photo into structured wardrobe data.

The solution

A Flutter client with a feature-first structure and a planned on-device pipeline: a clothing classifier, a dominant-colour module, and a compatibility scorer. The public v1.0.0 release ships the app foundation and camera flow while the model work is tracked openly in the repository's epic documents.

What is in the repository

  • Contributed the feat/app-foundation branch, merged through pull request #4: app shell, go_router navigation, Riverpod state, Material 3 theme, camera capture, and a refreshed widget smoke test.
  • The Flutter app declares go_router 17.5.0, flutter_riverpod 2.6.1, and camera 0.12.1 in pubspec.yaml.
  • The repository documents ten epics with explicit acceptance criteria; the foundation epic is marked complete and the model, storage, and cloud epics are marked not started.
  • The README publishes a signed APK download and installation notes for Android 7.0 and above.

Technical decisions

  • Kept the ML pipeline on-device in the plan (TFLite) rather than requiring a backend for every inference.
  • Used feature-oriented branches and pull requests instead of personal branches, with acceptance criteria written before implementation.
  • Documented incomplete epics as incomplete — the public task board is a status record, not a marketing page.

Challenges

  • The v1.0.0 app foundation and the ML pipeline are at different maturity levels. This portfolio separates the shipped foundation from the planned classifier rather than presenting the full concept as finished.

Verifiable results

  • v1.0.0 release published with an installable sera-z.apk.
  • Public epic tracker records E1 (app foundation) as complete; E6 and E8–E10 as partial; E2–E5 and E7 as not started at the time of review.
Evidence note

Team project by Kelompok 2. This case file credits the app-foundation branch and pull request visible under the Bisminee account; it does not claim the classifier or the entire application as solo work.

Case 03 Coursework 2026

Flutter Architecture Lab

Seven weeks of mobile coursework, ending in a clean-architecture refactor

A large Flutter learning repository: weekly exercises, a notes/announcements/settings app, a feature-first refactor, unit tests against fake repositories, and before/after documentation.

  • Flutter
  • Dart
  • Firebase
  • Clean Architecture
  • Unit testing
  • Git
Source for Flutter Architecture Lab (opens in a new tab)
Read the full case file

The problem

Learning Flutter screen by screen produces screens that work but do not scale. The final week asked for a structure that could survive new features and tests.

The solution

A week-by-week Flutter curriculum that culminates in a deliberate refactor: features grouped by domain, data sources behind repository contracts, use cases tested with fakes, and UI rebuilt against the new boundaries.

What is in the repository

  • Refactored the app into a feature-first clean architecture across notes, announcements, and settings.
  • Added unit tests for use cases using fake repository implementations.
  • Enabled the Google Services plugin and excluded Firebase configuration files from version control.
  • Documented the refactor with a README, an AI-challenge write-up, and before/after screenshots.
  • The repository also records a grep-based audit of three classic architecture violations before the refactor.

Technical decisions

  • Tested use cases at the boundary rather than mocking widgets, keeping domain tests fast and independent of Flutter rendering.
  • Treated the refactor as documentation work too: screenshots and a violation audit make the change reviewable.
  • Kept secrets out of the repository by ignoring Firebase configuration files and shipping only the plugin wiring.

Verifiable results

  • Week 7 commits show the completed refactor, the test suite, and the before/after evidence in the same history.
Evidence note

Solo coursework repository. The claims above come from the week 7 commit history and the repository README; no grades or performance results are asserted.

Case 04 Coursework 2026

Machine Learning Practicals

Notebooks on preprocessing, classification, and clustering

A semester of Jupyter notebooks covering exploratory analysis, feature scaling, label encoding, classification on the Titanic and Wisconsin breast-cancer datasets, and clustering on Iris and mall-customer data.

  • Python
  • Jupyter
  • pandas
  • NumPy
  • scikit-learn
  • Matplotlib
Source for Machine Learning Practicals (opens in a new tab)
Read the full case file

The problem

Models are only as trustworthy as the preparation behind them. The coursework focuses on the unglamorous middle: cleaning, encoding, scaling, and reading the results honestly.

The solution

Weekly notebooks that pair short explanations with executable Python. Each practical loads a dataset, inspects its shape and dtypes, prepares features, and applies a method appropriate to the task.

What is in the repository

  • Preprocessed the 569-row Wisconsin breast-cancer dataset with pandas, NumPy, LabelEncoder, and StandardScaler.
  • Worked with the Titanic dataset in multiple sessions, including a fixed and a selected feature set.
  • Explored clustering with the Iris and Mall Customers datasets.
  • Kept datasets, notebooks, and written README notes together so the work can be reproduced.

Technical decisions

  • Encoded the target before scaling numeric features, keeping the preprocessing order explicit in the notebook.
  • Separated columns that should and should not be used, rather than throwing every field at a model.
  • Stored the source CSVs alongside the notebooks for reproducibility.

Verifiable results

  • Six practical folders exist in the public repository, from fundamentals through clustering. No single benchmark score is claimed because the notebooks pursue different tasks.
Evidence note

Solo coursework repository. Notebook contents were inspected for the preprocessing steps and library usage described here.

Case 05 Coursework 2024–2025

Java Data Structures Lab

Linked lists, stacks, queues, and sorting built from scratch

A Java laboratory archive implementing core data structures by hand, with lab reports and a final queue-based academic service simulation.

  • Java
  • Object-oriented programming
  • Data structures
  • Algorithms
Source for Java Data Structures Lab (opens in a new tab)
Read the full case file

The problem

Using a library collection hides the mechanics. The lab required the mechanics: nodes, pointers, resizing, and the cost of each operation.

The solution

Implementations written directly in Java, paired with demonstration mains and PDF lab reports. The final exercise models a campus academic-service queue with separate student and service classes.

What is in the repository

  • Implemented singly and doubly linked lists with dedicated node classes and demonstration programs.
  • Built stack implementations, including a conversion stack and a student-task stack.
  • Built queue implementations and used them in an academic service simulation (SIAKAD).
  • Practised sorting algorithms and object-oriented class design across student, lecturer, and course models.

Technical decisions

  • Kept each structure in its own class with a separate main, so behaviour can be demonstrated without a framework.
  • Used custom node types rather than language collections to expose pointer manipulation.

Verifiable results

  • The repository preserves the implementations and lab reports from the course, including the queue-based service simulation.
Evidence note

Solo coursework repository. File names, implementations, and lab reports were reviewed; no grades are claimed.
